# 协作开发规范

## 1. 开始任务前

- 先阅读 README，确认任务目标、负责模块和完成标准。
- 一项任务对应一个分支；多人修改同一文件前，先协调分工。
- 改动公共接口或 Docker 环境前，先与受影响的成员确认。

## 2. 分支与提交

- `main` 保存团队已审核的版本，通过任务分支和 Pull Request（PR）合并。
- 分支名称使用英文小写、数字和连字符，例如 `feat/xt16-pointcloud`、`fix/tf-frame`、`docs/setup`。
- 每次提交只处理一件事；提交说明写清改动，例如 `feat: 增加巷道场景`、`fix: 修正雷达坐标系`。
- 开始工作和提交 PR 前同步 `main`；解决冲突后重新检查受影响内容。
- 合并到 `main` 前，至少由另一名成员检查；共享分支禁止强制推送。

## 3. 代码与 ROS 接口

- 保持代码简洁、命名清晰，保留必要的检查与错误处理。
- 代码与依赖需兼容 Ubuntu 20.04、ROS Noetic 和 Gazebo Classic 11。
- 算法、场景和传感器参数放入配置文件，避免写死个人路径、IP 和设备编号。
- 变更话题、TF、`frame_id`、消息字段、参数名或时间单位时，与使用方对齐并更新接口文档。
- 仿真节点统一使用仿真时间（`/use_sim_time=true`），核对 `/clock` 与消息时间戳。

## 4. Docker 与依赖

- 源码保存在宿主机并挂载到容器，在容器中编译和运行。
- 新增系统依赖写入 Dockerfile，ROS 包依赖写入对应 `package.xml`，其他依赖也需记录安装方式。
- 第三方代码记录来源、许可证和固定 commit；基础镜像记录标签与 digest。
- 环境改动后，从 Dockerfile 重新构建并验证，确保队友能够复现。
- 首次构建或录包前，补齐当前为空的 `.gitignore` 和 `.dockerignore`。

## 5. 文件与实验数据

- 文件与目录名称使用英文小写、数字、下划线或连字符；README.md、Dockerfile、CMakeLists.txt 等约定名称除外。
- 提交源码、配置、必要模型、小型测试样本和文档。
- 编译产物、日志、大型 rosbag、批量点云地图和镜像归档放在约定的存储位置，排除在 Git 与 Docker 构建上下文之外。
- 密码、令牌、SSH 私钥和个人环境配置不得提交；需要共享配置时提供不含凭据的示例。
- 实验记录写明代码 commit、镜像版本或 digest、场景、算法参数、数据位置、结果与已知问题。
- 比较算法或多轮地图时，记录所用数据和路线，保证结果可复核。

## 6. 验证与评审

提交 PR 时，简要说明改了什么、为什么改、如何验证，以及尚未验证的部分。

按改动范围选择检查：

- 文档或目录：检查描述、路径与链接；当前骨架阶段只需这类检查。
- ROS 代码或参数：在目标容器内编译，检查受影响节点、话题、TF 和时间戳。
- 仿真或算法：使用相关场景或固定 rosbag 回归，记录结果。
- Docker 环境：重新构建，检查 GPU、Gazebo 和 RViz；更新 README 中的环境说明。

检查通过并完成评审后再合并；发现缺陷时记录复现步骤与相关数据。
